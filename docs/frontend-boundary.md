# Frontend boundary baseline

This document records the pre-migration baseline for features 1–8. The enforcement test is `go test ./internal/architecture/...`; it scans every `.go` file under `internal`, regardless of the host platform or active build tags. `_test.go` files are excluded from production rules, and `internal/ui/uitest/shape.go` is classified through one exact test-support edge because its only importers are test files. `internal/architecture/testdata` is reserved for checker fixtures.

## Ownership and allowed dependencies

`main` is the concrete composition root. During migration, `internal/app` owns Bubble Tea orchestration and may use UI child packages, but its production calls are adapted behind consumer-owned capabilities as features 2–7 land. `internal/ui` owns interaction, navigation, presentation, messages and rendering. It may import `internal/api/contracts` and its own child packages. `internal/api/contracts` owns independent application inputs, facts, identities, revisions and outcomes; it must not import backend implementation packages, UI packages, Bubble Tea or Lip Gloss. `internal/ui/models` owns display rows and local drafts. Backend policy remains in `internal/api` and domain owners; backend packages may depend on contracts but not UI or terminal frameworks. Main remains responsible for concrete construction and process lifetime.

Root coordination may import children; views and components may not import `internal/app`. Views receive models and emit intents, not service handles. Consumer-owned interfaces group dashboard reads, card editing, session actions, configuration, center reads and attachment/deletion where appropriate. Keep interfaces beside current coordination until feature 7 moves the coordinator, then put them in `internal/ui/ports.go`. Exact Go signatures use independent contract types; the service does not import UI for conformance. Add contracts only with the feature that consumes them.

For frontend dependencies, forbid concrete `api`, `config`, `configstartup`, `session`, `driver` and `mcp` packages and descendants, except `api/contracts`. For backend dependencies, forbid UI and terminal-presentation packages. Inspect shared helpers transitively before treating them as neutral. The current `internal/ascii` dependency graph contains only ASCII helpers and `internal/ascii/characters` back to the helper package; it does not import backend packages.

## Contract and presentation conventions

Contracts contain application identity, policy facts, revision, inputs and outcomes. They do not contain aliases/embeds of backend records, repositories, managers, PTYs, UI/framework values, focus, keyboard shortcuts, styles, clipping or preformatted output. Presentation models own rows, resolved display data, selection and form drafts. Published slices/maps/buffers are detached or documented immutable; clone at the ownership boundary before local mutation.

Feature 2's first read family is dashboard inventory, scoped card/session summaries and action availability. Session summaries retain only current list needs: PID, workspace identity, registration and resolved active-conversation summary. Card summaries include identity, display name/appearance and capability references/details needed by current list/rendering consumers. Dashboard facts include identity, description/state and list action facts. Application supplies availability/reasons; execution revalidates. Unknown status has a safe display fallback and enables no unspecified action.

Later contract decisions: feature 3 uses opaque canonical full-record content revisions checked against current storage, no schema field, and presence-aware updates; feature 4 uses validated discriminated outcomes for pre-effect failure, usable activation, activation with metadata warning, cancellation and uncertain effects; feature 5 uses source expected-state identity and opaque change tokens with partial-read retention; features 6–7 use bounded center results and attachment input/output/resize/completion/release contracts that hide PTY ownership. These APIs are added only with their migrating callers.

## Checker limits and extension point

The normal test walks production files directly from disk, parses imports in every build variant and enforces exact file/import/rule/symbol/declaration-member-signature exceptions with one removal owner per type edge. A separate `type_exposure_allowlist.json` records reviewed transitive frontend type uses by file, declaration and source position, backend dependency, owner and reason; new alias uses fail unless individually reviewed. The graph follows value and pointer receiver methods, promoted methods from embeddings and imported frontend types, as well as package-level variable types. Type-expression traversal respects generic and receiver type-parameter scopes, including pointer generic receivers, so field names and shadowed identifiers are not treated as package types. Variadic element types and generic constraints are traversed through unions and approximation terms; an unsupported type-expression node fails the architecture check. Method declaration keys include normalized receiver identity. Transitive exposure entries use a validated feature 2–8 removal owner. The checker type-checks contracts packages with their effective transitive dependency variants, excludes `_test.go` files, resolves standard-library and sibling-contract imports, and traverses exported signatures and full type representations. Compatible contexts cover the toolchain-supported GOOS/GOARCH pairs, both cgo states, and assignments of up to eight custom build tags discovered across contract dependencies; cgo state participates in variant and importer cache identities. parents are checked again when a dependency selects different source files. Mutually exclusive declarations are checked in separate file sets. Unknown types, unresolved imports, unsupported tag explosion, parse/read failures and conflicting compatible package declarations fail with diagnostics. Contract type traversal includes private fields, aliases, embeds, methods, signatures, generic arguments/constraints, containers and local intermediate types. The dependency graph follows every permitted internal helper reachable from frontend code with cycle detection and propagates file errors. Checked-in fixtures and focused tests cover direct/reverse/root direction, arbitrary and cyclic helper paths, inactive imports and type graphs, clean real-path contracts with standard imports/local cycles/subpackages, forbidden aliases/embeds/nesting/methods/generics, unknown inactive types, exact and unused exceptions, same-selector new declaration edges, receiver-distinct same-named methods, local and imported indirect frontend aliases, method-set leaks through values/pointers/embedding/imports, field-name and generic type-parameter shadowing, pointer receiver parameter shadowing, variadic signatures, generic type/function constraints including aliases/unions/approximation, parent contracts across child platform variants, package variable alias exposure, cgo/non-cgo contract and dependency variants, neutral helper-to-contract paths, invalid owner and duplicate type-exposure exceptions, external/internal test files, and test-support misuse. The type graph reports the first forbidden chain per exported symbol; every direct forbidden import edge is still reported.
